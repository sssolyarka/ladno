# Архитектура и протокол

## Реализовано на этапе 1

Flutter/Dart: `lib/main.dart` содержит адаптивный интерфейс, очередь сохранения и обработку жизненного цикла. `lib/data/store.dart` — единая точка работы с SQLite, история, экспорт и проверка импорта. `lib/ai/provider.dart` — только контракт будущего ИИ-провайдера. API-ключей нет.

Android использует sqflite; Linux и Windows — sqflite_common_ffi с SQLite. path_provider выбирает пользовательскую папку. Точный путь виден в настройках. Данные не хранятся рядом с исполняемым файлом. Секреты в SQLite в будущем не помещаются: нужен Keychain/Keystore/Credential Manager/Secret Service.

Схема v1: `folders`, `notes`, `revisions`, `settings`. UUID v4 — постоянный идентификатор, `revision` — локальный порядковый номер, `updated` — UTC миллисекунды только для интерфейса. На часах не строится будущий порядок синхронизации. Изменения и история записываются в одной транзакции, `foreign_keys=ON`, `synchronous=FULL`, rollback journal DELETE. Закрытую базу перед будущим увеличением схемы копируем. Миграций между рабочими версиями пока нет: создана только v1; код миграции и аварийного восстановления надо добавлять и тестировать для каждого перехода. Более новая неизвестная схема отклоняется.

Markdown UTF-8 — канонический формат тела; поля заголовка и папки хранятся отдельно. Поддержан GitHub-подобный синтаксис заголовков, списков, чек-листов, ссылок. Редактирование пока текстовое, а не WYSIWYG. Внешние изображения заменяются текстовой подписью, ссылки копируются по явному нажатию. Объём истории: 30 предыдущих текстовых редакций; это не лимит суммарного размера базы. Формат резервной копии описан отдельно.

## Следующий этап: проект протокола v1 (НЕ реализован)

Ниже — спецификация намерений, а не обещание работающей сети. До реализации нужен прототип TLS/QR/mDNS на всех трёх ОС и тестовый транспорт с воспроизводимыми сбоями. Не передавать пользовательские данные по временному незашифрованному протоколу.

### Транспорт и доверие

Оба узла равноправны. На ПК доступен локальный listener, телефон может инициировать соединение; узел с другой стороны тоже принимает изменения. mDNS/DNS-SD `_ladno._tcp.local` рекламирует только версию и случайный ID, без заметок и токенов. При блокировке multicast — адрес из QR или ручной ввод. В межсетевом экране ПК нужен доступ только из доверенной локальной сети, не открытый интернет-порт.

TLS 1.3 с взаимной проверкой закреплённых сертификатов; использовать зрелый TLS стек (например, rustls через проверенный нативный мост), системный CSPRNG и системное защищённое хранилище. Не писать криптографические примитивы на Dart и не отключать проверку сертификата через безусловный `badCertificateCallback`. Выбор конкретного моста — задача этапа 2, требующая проверки Windows 10 и Android.

Связывание: ПК генерирует короткоживущий одноразовый секрет 256 бит, срок 2 минуты. QR содержит адрес, версию, SPKI fingerprint сертификата и секрет; не содержит заметок или постоянного приватного ключа. Телефон сканирует QR, закрепляет сертификат для этой сессии и доказывает владение секретом внутри TLS. На обоих устройствах выводится один fingerprint сессии/код сравнения, полученный проверенной библиотекой из транскрипта. Пользователь подтверждает на обоих. Только после двух подтверждений публичные ключи становятся доверенными. Таймаут и ограничение попыток, удаление временного секрета. Без подтверждения доступ к данным запрещён. Смена ключа требует нового связывания.

Отзыв доверия удаляет peer из allow-list; его TLS запросы отвергаются, outbox для него удаляется. Существовавшие у него данные удалённо не стираются. Доверие и ключи исключаются из экспорта.

### Журнал операций и подтверждения

Будущая схема v2: `devices`, `operations`, `object_heads`, `peer_acks`, `conflicts`, `attachments`, `transfer_chunks`. Каждая операция имеет `(origin UUID, monotonic counter)` как ID, `objectId`, тип, список родительских operation IDs, версию формата, изменённые поля и состояние удаления. Счётчик увеличивается транзакционно с локальным изменением. Копирование базы на другой узел нельзя использовать для создания устройства с тем же origin.

Изменение хранится локально до получения от каждого доверенного peer **durable ACK**, отправленного только после успешной транзакции. При обрыве отправка возобновляется с вектора подтверждённых счётчиков и перечня пробелов. Приём имеет UNIQUE(origin,counter); повторная доставка не порождает новой операции и нового UUID, а возвращает тот же ACK. Полученные операции не переписываются от имени получателя — циклы не создают изменения. Зависимости отсутствующих родителей запрашиваются; необоснованный скачок счётчика не продвигает подтверждение через пробелы. Устройства могут иметь различающиеся часы, порядок задают причинные родители и счётчики.

Успешная синхронизация означает подтверждение текстовых операций обеих сторон; вложения имеют отдельный статус. HELLO обменивается диапазоном версий протокола и схемы объектов. При отсутствии общей версии — понятный отказ, без записи частичных новых данных и предложения «сбросить базу». Размеры сообщений, поля и частота запросов ограничены.

### Конфликты и удаления

Потомок заменяет предка. Разные поля конкурентных операций объединяются. Конкурентные значения одного обычного поля выбираются детерминированно по `(counter, origin)` только как отображаемое значение; проигравшие значения остаются в журнале и карточке конфликта. Это не сравнение реального времени.

Конкурентный заголовок или Markdown сохраняется обеими редакциями с видимым конфликтом. Никакого невидимого last-write-wins текста. Разрешение пользователем — новая операция со всеми конфликтующими heads как родителями; появляется единый head. Удаление против редактирования остаётся конфликтом: запись в корзине, текст редактирования доступен для восстановления. Обычное удаление — tombstone, а не физическое исчезновение. Восстановление — новая операция, явно ссылающаяся на удаление.

На первом сетевом этапе tombstones и журнал хранятся **бессрочно**, без автоматического удаления по возрасту. Это намеренный компромисс ради давно отсутствующего устройства. В дальнейшем compaction допустим только после подтверждения всех доверенных peer либо после их явного отзыва и нового sync epoch. Старый peer с неподдерживаемым epoch должен сначала сохранить локальную копию, затем пройти полную сверку снимка и перенести неподтверждённые операции; нельзя просто залить старую базу поверх свежей. Пересвязывание создаёт новый origin, исключая коллизии счётчиков.

### Вложения

Метаданные отдельно от файлов. Файлы адресуются SHA-256, имя пользователя не становится путём. Сначала синхронизируется текст, затем блоки ограниченного размера в `.part` с bitmap полученных частей. Повтор блоков идемпотентен. Размер, хеш полного файла и лимиты проверяются до атомарного rename; оборванные файлы не объявляются доступными. Неполные файлы можно докачать. Физическое удаление после отсутствия ссылок и подтверждённых tombstones, по отдельной политике очистки.

### Запуск и фон

Полная попытка синхронизации при запуске, возврате на экран, появлении сети и кнопке пользователя. На ПК — пока приложение работает. На Android — надёжно только при открытом приложении; WorkManager может предоставить отложенную попытку, но не постоянный listener и не гарантию времени. Foreground service только как отдельный явный режим с постоянным уведомлением и с учётом ограничений Android. После Force stop пользователь должен открыть приложение. Без связи локальное сохранение работает самостоятельно.

## Последующие модели

Повторы задач: deterministic occurrence ID от series UUID + schedule revision + occurrence index, UNIQUE на этих полях. Выполнение создаёт одну транзакционную операцию и следующий экземпляр; повторы после завершения зависят от события завершения, а не времени последнего синка. Пересекающиеся завершения разрешаются по одному логическому occurrence; тестировать на двух узлах до выпуска.

Привычки: отдельная дата `YYYY-MM-DD` + IANA timezone расписания, отметка уникальна для habit/date. Смена зоны не переписывает прошлые даты автоматически. Фокус: сохранять start/end и elapsed-before-pause; после возврата вычислять остаток по timestamp, не только по тикам UI. Проверять перевод часов и перезапуск.

Уведомления: стабильный notification ID на reminder UUID; upsert/cancel при изменении и синке. Android 13+ POST_NOTIFICATIONS; exact alarms отдельно и только если разрешены. Перепланировать после перезагрузки, смены зоны и обновления. Fedora: desktop notifications только с работающим процессом; для закрытого приложения нужен проверенный пользовательский systemd timer/service. Windows: отдельно проверить toast scheduling/activation. До этих тестов не заявлять уведомления при закрытом приложении.

ИИ: выбранный пользователем фрагмент показывается перед запросом, отмена и бюджет обязательны. Результат — предложение с просмотром перед применением. Ни автоматической передачи, ни общих ключей разработчика, ни текста заметок в логах.

## Состояние реализации второго этапа

Фактические модули и ограничения перечислены в [STAGE2.md](STAGE2.md). Журнал использует причинные родители и логические часы; все операции и отметки удаления пока хранятся без автоматической очистки. Повторяющийся идентификатор с другим содержимым отклоняется. Получение и отображение заметки фиксируются одной транзакцией; ACK означает запись после commit. Неполный ребёнок хранится до прихода родителей. Протокол ограничивает пакет 64 операциями/8 МиБ, одну операцию 4 МиБ; слишком длинные и несовместимые сообщения отклоняются.

Параллельные значения полей сохраняются; детерминированное отображение не удаляет другие варианты. Удаление выигрывает только отображение; конфликт с редактированием сохраняет текст. Диалог объединения использует ровно те родители, которые он показывал, поэтому поздняя редакция не будет молча поглощена. Папки с отметкой удаления скрываются из выбора, записи и причинные связи остаются. Конфликты папок пока доступны через модель, отдельного диалога нет.

TLS-модуль требует TLS 1.3, сертификат клиента и точный отпечаток доверенного устройства. Запрос без сертификата получает отказ до доступа к маршрутам данных. Генерация/защищённое хранение ключей и QR-связывание ещё не подключены: временные ключи тестов не используются приложением. Нет незашифрованного сетевого обхода. Вложения проверяются SHA-256 и публикуются после полной проверки; отсутствующие файлы отделены от результата обмена текстом.
